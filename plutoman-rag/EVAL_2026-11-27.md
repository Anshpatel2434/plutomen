# Full regression after the contrastive and observation-note fixes

Measured overnight 26–27 Nov 2026 against `fix/chat-follow-up-narrowing` at
`b29bc14`. 153 questions in one unbroken run: the client's golden set (40),
frozen held-out v1 (36) and v2 (36), and the new self-written held-out v3 (41).
`CACHE_ENABLED=false`, `VERIFY_ANSWERS=true`, mistral on the GPU, same harness
and graders as every previous round.

The purpose of the run was not a higher score. It was to establish that two
fixes landed and that nothing which worked before stopped working.

## What this round changes

| Commit | |
|---|---|
| `952c2c7` | a contrastive follow-up never reaches the data engine |
| `b29bc14` | an observation's note is read, not dropped |

**`952c2c7`** moves the contrast step above the data engine in `chatTurn`. The
engine answers from model-written SQL and has no way to express "any report
except the one we just discussed", so on a contrastive turn it could answer
about the report the question excludes. It now sits that turn out, and so does
`tryCompute`. Pure ordering; four source-reading guards in
`test/contrastRouting.test.ts` pin it, because the defect was one of order and
nothing else would catch a re-ordering.

**`b29bc14`** is the one that touched data. The Observations sheet keeps the
inspector's note in column 5 and nothing read it: `parseXlsx` took the index and
the Answer text only, `Observation` had no field for a note, and `buildFacts`
passed `null` where every other area passes the note through. The note therefore
reached neither the chunks nor the fact table — the system was not withholding
it, it had never seen it. Five notes across four reports were lost, and the loss
is worst on the cable reports, where the Answer column holds only a severity
("Critical") and the substance is the note.

Reading the column was necessary but not sufficient. Appended bare, as
`Critical - Requires vendor CAPA and re-inspection.`, the model held the chunk
and still said no note was recorded: an observation's answer is often a lone
severity, so the trailing clause reads as one sentence. Labelling it
`(note: ...)` — the form `buildFacts`' own summary already uses — made it
answerable. The note is deliberately kept out of the `answer` field, which is
what `locateChunks` matches against to find printed page numbers; folding it in
would cost every observation its page citation.

Re-ingestion was taken against a `pg_dump` safety point. Counts unchanged
(630 chunks / 597 items / 118 amounts), observation notes 0 → 5, and all 11
reports still report 100% PDF twin match.

### Two cases that moved the other way

**v1 H07 — a real regression, not attributable to either fix.** Asked what
powder coating thickness was observed at the corners, the system answered "Ok"
— the Characteristics verdict — instead of the observation that records
60–70 microns. The previous run answered it correctly. The relevant chunks in
that report carry no note, so `b29bc14` left their text and embeddings
byte-identical, and the question is single-turn, which `952c2c7` cannot reach.
This is generation choosing the wrong field between two runs of identical input.

**v2 V31 — a real regression, and this one is attributable to `b29bc14`.**
Asked what NCR was raised for missing water blocking in the KEI conductor, the
system correctly says none was raised, but now reasons from the observation note
I added — "no blocking issue on observation point 2" — instead of the p.4 line
recording the water blocking as verified against the QAP. The verdict is right
and the evidence is wrong. The note is a lexical lure for a question about
"blocking", and before the fix that string was not in the index at all.

This is the honest cost of the fix: it raised recall on observation notes and
introduced one distractor. The alternative is the false absence the fix exists
to remove, so the trade looks right — but it is a trade, and it is worth
revisiting if more cases of this shape appear.

### Two apparent regressions that are not system defects

- **v1 H18.** The new answer is correct, cited, and names the rectification
  condition; the criterion requires the literal word "cleared", which the old
  raw field dump contained by accident and clean prose does not. A criterion
  defect in the v1 set, left as-is because that set is the client-facing frozen
  baseline.
- **v3 W05.** The previous pass was coincidence. Both runs misidentify whose
  inspections are being asked about in the follow-up: the older answer named the
  wrong engineer but happened to list two job ids the criteria required, the new
  one names a different wrong engineer. The underlying defect — a pronoun in a
  follow-up resolved inside the data engine — is unchanged and pre-existing.

**v2 V35 and V36 were never run on 25 Nov** (that run stopped at 34 of 36), so
they are first measurements, not movement. V36 passes; V35 fails on the
PO-number-in-a-follow-up defect already recorded as W07.

## Latency, and the one operational finding

| Set (in run order) | mean | median | > 180 s | worst |
|---|---|---|---|---|
| Golden | 68.0 s | 38.8 s | 2 | 890 s |
| Held-out v1 | 55.3 s | 52.1 s | 1 | 220 s |
| Held-out v2 | 64.6 s | 55.6 s | 1 | 185 s |
| Held-out v3 | 146.2 s | 87.7 s | 9 | 674 s |

The v3 set is frozen and was run twice: 46 minutes on a freshly restarted
stack, and 100 minutes as the fourth set of a long run, with the same questions
and the same answers. Median doubles and nine questions cross three minutes.

This is the `mistral` capacity ceiling, not a code path: 5.6 GB at
`CONTEXT 8192` does not fit 4096 MiB of VRAM, Ollama splits it 60% CPU / 40%
GPU, and prefill goes CPU-bound as prompts lengthen. It degrades with uptime
rather than with the question. **Accuracy does not suffer — v3 scored the same
on both runs — but a demo an hour in will feel much slower than a demo on a
fresh stack.** A restart before a client session is the cheap mitigation; the
real fix is a smaller quantisation or more VRAM.

## The grader correction

v3 Z02 asks what drum length was verified against a PO. The system answered
"250 mtr … POID-4547081947, PH2026100008" — correct — and was scored a fail,
because the criterion forbade the string `1000` (a wrong drum length elsewhere
in the corpus) and `1000` occurs inside the job id `PH2026100008`.

Same class of defect as the single-digit criteria corrected before the first
run. The criterion is now `1000 mtr` / `500 mtr` in phrase form, no question or
expected answer touched, and the set re-frozen
(`9aea7457…` → `3299d927…`, reason recorded in `FROZEN.txt`). The grader
self-test still holds: ideal answers 41/41, junk answers 5/41.

An audit of all three held-out sets for criteria short enough to match inside a
report or job id found this one case and no others; the remaining short numeric
criteria were checked individually and none is currently passing on an id
substring.

## Reproducing

The harness, the golden questions, the gold answers and the frozen held-out
sets are the client's material, or derived from it, and are deliberately **not**
in this repository. Run outputs are kept in the working copy, untracked:
`eval_runs_2026-11-27/` (this round, with the v3 harness and the pre-ingestion
dump) and `eval_runs_2026-11-25/` (the previous one).

```bash
CACHE_ENABLED=false docker compose -f docker-compose.yml -f docker-compose.gpu.yml --profile app up -d
bash eval_runs_2026-11-27/heldout3_harness/run_all.sh    # all 153, then all four graders
```

Full test suite: 219 pass. `CACHE_ENABLED` was returned to the repo default
(`true`) after the run; it is `false` only because the harnesses require it.
